# Canon: M5 implementation plan (Publish)

Status: **approved 2026-10-29** ("yeah go ahead": H1 to H5 as recommended). Decisions recorded as D51 to D55.

M5 is the first milestone that writes to the public bucket. For every item marked `public`, apply copies the files its views use to `gs://canon-public` and writes the public manifest: drafts dropped and private fields stripped. It also writes one view per surface (`views/<surface>.json`), resolved from the frozen M1 view schemas. Unpublishing removes what no public item uses anymore. The design doc's "Surface views" and the M0–M1 plan §2.4 are the spec for each view.

What's real today: all 135 items are drafts and **no item has a placement**, so every view would be empty. Placements and visibility are content decisions (H5).

## 0. Decisions

### 0.1 Need your call

| # | Question | Recommendation |
|---|---|---|
| H1 | **Which files a public item exposes.** The private bucket holds each sanitized source at full resolution (your paintings up to 22 MP), plus the M4 outputs. | **Only what a view links to:** for images that's the `thumb` sizes (at most 3200 px) and the `lqip`; for tracks the source MP3, the `djgrid` analysis and the previews; for video the `web` encode and the poster. Full-resolution sources stay private, so nobody can download a 22 MP original of a painting. The other option is to also publish each source blob (as the design doc's `blobs/...` row implies), which makes full-res downloads possible. |
| H2 | **Unpublishing for real.** The public bucket has object versioning on (M0 provisioning), and anyone can read a deleted file's old version if they know its generation number. | **Turn versioning off on the public bucket** and keep its 30-day soft delete. The public bucket is a projection, and apply can rebuild all of it from the private one. A soft-deleted file isn't readable by anyone until you restore it, so unpublish really takes it down. `provision-buckets.sh` changes accordingly (D-entry); the private and archive buckets keep versioning. |
| H3 | **Cache lifetime of public copies.** The design doc says `max-age=31536000, immutable` (1 year). Content-addressed paths never go stale, but an unpublished file stays in browser and Google edge caches for as long as it was told to. | **1 day** (`public, max-age=86400`) for `blobs/` and `derived/`, and 60 s for the manifest and views (as designed). An unpublished piece is gone everywhere within a day, and browsers only re-check unchanged files once a day. Keep 1 year if you'd rather have the most caching and accept that unpublishing is slow. |
| H4 | **Public URLs.** | **`https://storage.googleapis.com/canon-public/...`**, from a new optional config field `publicBaseUrl`. Point that at a CDN or your own domain later; views then change, and files don't move. |
| H5 | **What to publish when M5 lands.** | **Nothing automatically.** M5 ends with `canon view <surface>` previews built from your working manifest, for you to review. Then, as a separate step you approve, I'd add placements for the 7 collections on `holodeck-art-room` and `music` on `holodeck-dj-room`, and mark them and their pieces public, except the 3 sketches marked private in the old bucket. Nothing goes public until you say which. |

### 0.2 Defaults I'll take unless you object

- **The public projection is an allowlist:**
  - Only `visibility: public` items.
  - No `private` block, and no `assets[].original` (D28).
  - Collections' `members` keep only public ids (D25).
  - Placements on draft items disappear with the items.
  - The result must validate against `public-manifest.schema.json`, or there's no plan.
- **Views come only from the public projection,** never from the working manifest, so a view can't mention a draft. `canon view <surface>` (the preview) resolves the working manifest instead, and says so in its output.
- **Resolution, per §2.4:**
  - Copy resolves field by field: placement, then `copy[surface]`, then item.
  - `hidden` placements are dropped.
  - Entries are sorted by `order`, then `date.sortKey` descending, then `id`.
  - The view's taxonomy holds only the slugs it uses.
  - `date.display` comes from the label, or from the value (`2024`, `Dec 2024`, `Dec 3, 2024`). `sortKey` is `YYYYMMDD` with `00` for anything missing.
- **Resolved images** (`resolvedAsset`):
  - `url` is the largest thumb, `srcset` all of them, and `width` and `height` come from the largest.
  - `lqip` is the `lqip@v1` WebP as a `data:image/webp;base64,...` URI.
  - `alt` comes from the asset's `alt`, else null.
  - An image whose jobs haven't finished leaves its entry out of the view, with a plan warning, so a view never links a missing file.
- **DJ room:** `audio` is the `dj-mp3@v1` output for lossless sources, or the source MP3 itself (D49). `analysis` is the `djgrid@v1` `analysis.json`, and the facts give BPM, key and the rest (D48). `artist` comes from the Music collection's first credit, falling back to the profile name. The schema's "192 kbps MP3 from dj-mp3@v1" description gets a note for MP3 sources.
- **The other five surfaces** (`nickel-desktop`, `software-portfolio`, `design-portfolio`, `art-portfolio`, `holodeck-showroom`) are built and tested against fixtures, per §2.4: preview `auto` uses `embeddable` plus the live link, and `filters` are sorted most used first. Nothing in your data places on them yet; `content.ts` (M7) brings the projects.
- **Ops and order:**
  - Order: `archive-original` → `upload-blob` → `run-job` → `publish-copy` → `write-manifest` → `write-history` → `write-view` → `write-public-manifest` → `unpublish`.
  - Every file a view or the public manifest links is in place before either is written.
  - Unpublish runs last, after nothing links its files.
  - `publish-copy` is a server-side copy from private to public (no download), under the same path, with `Cache-Control` per H3.
  - Views and the public manifest are written only when their bytes change, so an unchanged manifest gives a plan with no writes.
- **Unpublish:** any object under `blobs/` or `derived/` in the public bucket that nothing public needs anymore. Each one is a plan line naming the file, and apply deletes it. This is the only delete in Canon before M8.
- **Determinism:** views and the public manifest use canonical JSON (sorted keys, 2-space indent). `pipelineVersion` is Canon's version (`0.5.0` for M5). No timestamps, as D12 requires.
- **Go view types (D23):** hand-written structs per view in `engine/views`, each checked against its schema on every resolve and in tests. That gives strict Go types without go-jsonschema's `$ref` bug.
- **Import redirects (D43):** apply writes `<state>/imports/<bucket>-urls.json`, mapping each old object's public URL to its item's new image URL. It covers published items only, so the holodeck can switch over URL by URL.
- **API:** `listSurfaces` and `previewSurface` (frozen in M1) get handlers; the CLI is `canon view` and `canon view <surface>`. No spec change needed. The OpTypes `publish-copy`, `unpublish`, `write-view` and `write-public-manifest` are already in the enum.
- **GCS:** the API grows `Copy` (server-side, conditional like every write) and `Delete` (with `ifGenerationMatch`), both on the in-memory fake too. Config gains `publicBaseUrl`. Plan and apply need `publicBucket` once anything is public.

## 2. Tests

| Area | Test |
|---|---|
| Projection | Drafts, private blocks, originals and draft members never appear (property test over random manifests); the result validates against the public schema; the existing `schema/testdata/public` fixtures behave as named. |
| Views | Each resolver against the M1 view fixtures (golden) and its schema; copy precedence; hidden placements; sorting; taxonomy limited to what's used; a draft never appears; an image with missing outputs is left out with a warning. |
| Determinism | The same manifest gives byte-identical views and public manifest, twice. |
| Plan and apply | Publish → plan is empty → unpublish one item → its files leave the public bucket, the views and public manifest stop mentioning it, and a draft's files never reach the public bucket at all. A failure at every write converges; a public file is never linked before it exists. |
| Cache headers | Every public object has its H3 header; no private-bucket object is ever written to the public bucket except through publish-copy. |
| Real data | `canon view holodeck-art-room` and `holodeck-dj-room` on your working manifest validate against their schemas. Publishing them is the H5 step. |

**M5 is done when** the above pass, and the plan for your real data (with nothing public) writes only an empty public manifest and empty views. Then H5 is your call.

## Built (2026-10-29)

Everything above is in. On the real data, `canon-public` lost its versioning (D52, through `provision-buckets.sh`), `canon plan` reran `thumb` at v2 (D56) and planned the 7 empty views and the empty public manifest, `canon apply` wrote them (129 ops), and the next plan printed "No changes." The public bucket holds those 8 files and nothing else.

- **Tests:**
  - The projection is checked by a 200-round property test (drafts, private notes and original hashes never reach the public bytes) and by a test that fails when `Item` gains a field the projection hasn't decided on.
  - Each view has a golden file built from `valid/full.json` and checked against its schema.
  - Publish, then unpublish, runs end to end on the in-memory fake: files leave the public bucket, views stop mentioning the item, cache headers are per D53, and a draft's outputs exist privately but never publicly.
  - A failure at every public write converges, and no view ever links a missing file.
- **Found while building:**
  - A working manifest made from scratch declares no surfaces, and a placement can only name a declared surface. So none of the imported items can be placed yet, and the H5 step has to declare the surfaces it uses first. There's no command for that yet (see below).
  - The DJ crate's artist fell back to the profile name, though every track is credited to Bird Dog (D57).
- **Not done:** the `--drafts` preview of your real art and DJ rooms. It needs placements, which is the H5 step. The fake-gcs-server integration suite still can't run here (no Docker).
