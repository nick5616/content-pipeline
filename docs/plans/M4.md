# Canon: M4 implementation plan (Derived jobs)

Status: **approved 2026-10-29** ("yeah": G1 to G6 as recommended). Decisions recorded as D45 to D50.

M4 turns each sanitized blob into the files and facts the sites need: image sizes, placeholders, palettes, video posters and web encodes, audio previews and waveforms, and the DJ room's beat grids. Each comes from a named, versioned recipe, keyed by exactly what produced it (design doc, "Derived assets as jobs"). Outputs reach the private bucket through the same plan and apply as blobs. Publishing them is M5.

Real data to cover: 121 artworks (two of them HEIC, which browsers can't show) and 7 MP3 tracks, now in `gs://canon-private`.

## 0. Decisions

### 0.1 Need your call

| # | Question | Recommendation |
|---|---|---|
| G1 | **When jobs run.** Facts recipes (palette, beat grid) write into the working manifest, and F2 says apply writes exactly the manifest you planned. So those jobs can't run during apply. | **Jobs run locally, and `canon plan` runs any pending ones first** (with progress; `--no-jobs` skips them). The plan then only uploads finished outputs, as `run-job` ops. `canon jobs run` runs them on their own, and `canon serve` runs them in the background after ingest. The other option is to run jobs only by hand: `plan` would then list "N jobs haven't run" as an error until you run `canon jobs run`. |
| G2 | **Image tool.** Your art includes Display P3 files (the iPhone HEICs, for one). | **libvips** (`vips`, 8.15 on Ubuntu, Homebrew on the Mac): it converts each image to sRGB using its color profile, reads HEIC through libheif, auto-rotates, and writes WebP. It's a new dependency in bootstrap and doctor. ffmpeg already has a WebP encoder, but it ignores color profiles, so P3 art would come out with shifted, duller colors. |
| G3 | **Image widths** (`thumb@v1`). The portfolios use 320, 800 and 1600; the holodeck loads 48, 2048 and 3200 through Netlify's image CDN. | **320, 800, 1600, 2048 and 3200, never upscaled**: widths wider than the source are dropped, and the source's own width is added as the largest (a 2562 px piece gets 320, 800, 1600, 2048 and 2562). WebP quality 80, the holodeck's setting. The holodeck's blurry 48 px preview becomes `lqip@v1`. Once views (M5) point at these, the Netlify CDN step goes away. |
| G4 | **A fact a recipe computes vs. one already set.** Your 7 tracks already have BPM, key and beat grid from `crate.json`, computed from the AIFF masters. `djgrid@v1` would recompute them from the MP3s, which is slightly less accurate. | **Recipes only fill empty facts.** Your imported values and any hand edits stay; `canon jobs run --refresh-facts` overwrites them on purpose. The waveform file is always made, since nothing provides it today. |
| G5 | **`dj-mp3@v1` on MP3 sources.** All 7 tracks' sources are already 192 kbps MP3s; the AIFF masters were never in the bucket. | **Only for lossless sources** (AIFF, WAV, FLAC). An MP3 source plays as it is: re-encoding MP3 to MP3 only loses quality. Ingesting a master later gets the 192 kbps encode. |
| G6 | **Additive API change, 1.2.0 → 1.3.0.** Nothing in the spec starts jobs. | Add `POST /api/jobs/run` (`runJobs`, CLI twin `canon jobs run`). The `Job` schema, `listJobs` and `retryJob` already fit. `run-job` ops stay as they are in the spec; they mean "upload this job's outputs". |

### 0.2 Defaults I'll take unless you object

- **Which assets get which recipes:**
  - **Images** (artwork and photo assets): `thumb`, `lqip`, and `palette` (on the item's first image only).
  - **Video:** `poster` and `web`.
  - **Audio:** `preview`, `peaks` and `djgrid`, plus `dj-mp3` for lossless sources (G5).
  - **PDFs:** nothing in v1.
- **No job chains in v1.** `poster@v1` writes its frame at the `thumb` widths itself. A chain would need the poster's hash before the thumb's job key exists, which breaks planning ahead.
- **Every derived file passes the same verify gate as ingest** (fail closed), so nothing reaches a bucket that the verifier hasn't passed. The private-bucket uploader keeps taking only blob-store types, so an unverified file can't be uploaded.
- **Layout:** `<cache>/derived/<jobkey>/<file>` locally, `derived/<jobkey>/<file>` in the private bucket, plus `derived/<jobkey>/job.json` listing each file's sha256. `job.json` uploads last, so a job is done remotely only when its receipt is there.
- **Idempotent by key across machines:** before running, the runner checks the private bucket for `job.json`. If it's there, the job is done without running (the Mac and WSL never both encode).
- **Job keys:** `sha256(sourceSha256 + recipe + version + canonicalJSON(params))`. Tool versions aren't in the key: Homebrew and Ubuntu ship different vips versions, and putting them in would rebuild everything on each machine. A tool upgrade that changes output means bumping the recipe version (doctor already warns when a tool changes).
- **The recipes:**
  - `thumb@v1`: WebP at the G3 widths, sRGB, no metadata.
  - `lqip@v1`: 32 px wide WebP, quality 40, stored as a file. M5 inlines it in views as a data URI. That adds no manifest field, and the design's "inlined in the manifest" becomes "inlined in views".
  - `palette@v1`: 5 colors by deterministic k-means in Go, on a 64 px sRGB render, written to `facts.palette`.
  - `poster@v1`: the frame at 10% of the duration, as WebP at the thumb widths.
  - `web@v1`: H.264 MP4, CRF 23, `-preset veryfast`, faststart, AAC 128 kbps, at most 1920 px wide, no metadata.
  - `preview@v1`: 128 kbps MP3 of the whole track, plus a 30-second clip from one third in, with 1-second fades.
  - `peaks@v1`: 1000 min/max pairs as JSON.
  - `dj-mp3@v1`: 192 kbps, stereo, 44.1 kHz (G5).
  - `djgrid@v1`: BPM, first beat, start, key and Camelot code into facts (G4), plus `analysis.json` in the crate's format (`{fps, bands, waveform}`), so the DJ room reads it unchanged.
- **djgrid parity:** the DSP from `scripts/build-dj-crate.mjs` (3d-portfolio-website @ 872f68a) is copied into `testdata/djgrid/reference.mjs` with a small wrapper. A test runs both on the same fixture audio. BPM and key must match, the first beat must be within 1 ms, and waveform bytes within ±1. The test is skipped if Node is missing. As a manual check, I'll also run it on your 7 MP3s against `crate.json`.
- **Job state:** SQLite (`modernc.org/sqlite`, pure Go) at `<state>/jobs.db`: jobkey, recipe, source, item, state, attempts, last error, timestamps. Desired jobs are recomputed from the manifest on every run. A job whose blob is no longer referenced is left alone; its outputs become orphans for M8.
- **Workers:** CPU count, with at most 2 ffmpeg jobs at once. One runner per machine (a lock in the state dir, shared by the CLI and `serve`).
- **Retries:** tool errors (a bad input) fail at once and show the tool's output. Network errors during the remote check retry 3 times with backoff and jitter. `canon jobs retry <jobkey>` requeues a failed job.
- **CLI:** `canon jobs [--state failed]`, `canon jobs run [--item slug] [--recipe name] [--refresh-facts]`, `canon jobs retry <jobkey>`. `--watch` stays with SSE in M6.
- **Doctor and bootstrap:** add `vips` (`libvips-tools` on Ubuntu, `vips` from Homebrew), with its version recorded like the other tools.

## 1. Flow

```
canon plan
  1. desired jobs = manifest assets x recipe registry          (pure)
  2. skip jobs whose receipt is local or in the private bucket
  3. run the rest: tool -> temp dir -> verify -> <cache>/derived/<jobkey>/
     facts recipes fill empty facts in the working manifest   (store.Update)
  4. diff: run-job op for every job whose receipt isn't remote
apply (order)
  archive-original -> upload-blob -> run-job (files, then job.json) -> write-manifest -> write-history
```

If apply dies before `write-manifest`, the remote manifest still points only at files that exist (design doc, "Ordering"). A `run-job` op that dies partway leaves no receipt, so the next plan lists it again, and the files already uploaded are skipped by checksum.

## 2. Files

```
engine/recipes/          registry, one file per recipe (name, version, params, applies-to, run)
engine/recipes/djgrid/   the DSP port (tempo, key, start, waveform), table- and parity-tested
engine/jobs/             job keys, the SQLite store, the runner (pool, ffmpeg cap, remote check, lock)
engine/derived/          the local derived store and verified outputs (like blobstore)
engine/plan, apply       run-job ops: diff against derived/ listings, upload outputs then the receipt
api/, internal/cli/      jobs, jobs run, jobs retry (API 1.3.0, G6)
testdata/djgrid/         reference.mjs (copied DSP) + its wrapper
```

## 3. Tests

| Area | Test |
|---|---|
| Job keys | Same inputs give the same key; a change to source, version or params changes it; params are canonical JSON (key order doesn't matter). |
| Recipes | Each recipe runs on the fixture media and its outputs pass verify. Widths are never upscaled. P3 input comes out sRGB (a known P3 red lands on the right sRGB value). HEIC works. EXIF rotation is applied. Palette and peaks are deterministic. |
| djgrid | Parity with `reference.mjs` (above); synthetic clicks at a known BPM and key; silence and very short files. |
| Runner | Rerunning does nothing; a receipt already remote means nothing runs; a crashed job leaves no output; tool failure vs network failure; at most 2 ffmpeg jobs at once; two runners can't both run. |
| Facts | Recipes fill empty facts only; `--refresh-facts` overwrites; a hand edit survives a rerun. |
| Plan and apply | Ingest, plan (jobs run), apply, plan → "No changes." Kill apply mid-upload of a job's files; a rerun converges and the receipt is last. Also run against fake-gcs-server. |
| API | `runJobs`, `listJobs`, `retryJob` against the 1.3.0 spec, with CLI twins. |

**M4 is done when** the above pass, and on your real data `canon plan` runs every job, `canon apply` uploads them, and the next plan prints "No changes."

## Built (2026-10-29)

Everything above is in. The done criterion holds on the real data: `canon plan` ran all 384 jobs (121 artworks × thumb, lqip and palette; 7 tracks × preview, peaks and djgrid) in under a minute with none failing, filled 121 palettes and left the tracks' imported facts alone (D48). `canon apply` uploaded them to `gs://canon-private` (386 ops), and the next plan printed "No changes."

- **djgrid parity:** the port matches `reference.mjs` exactly (BPM, key, first beat, start and every waveform byte) on the synthetic cases. On the real crate it matches `crate.json` on 6 of 7 tracks; Unethical (Sauced Up) reads 128.69 BPM from its MP3 against 130 from its master, and the script does too. The script also reads a synthetic 128 BPM loop as 113.56, so that case is held to parity only. `DJGRID_CRATE=<dir> go test ./engine/recipes/djgrid -run RealTracks -v` reruns the real comparison.
- **Found while building:**
  - Job state writes serialized the workers: each SQLite commit waited for an fsync, which is slow on WSL. The job database uses WAL with `synchronous=NORMAL` now.
  - A problem with no path printed `at :`, including M3's archive-checksum error. `Problem.String` now leaves the location out when there isn't one.
  - A receipt for a job with no files (palette) wrote `"files": null`; it's `[]` now.
  - `canon plan` reports jobs only when one ran, failed or filled facts, so a plan with nothing to do prints only "No changes."
- **Not run here:** the fake-gcs-server integration suite (Docker isn't available in this WSL distro). The apply job tests run against the in-memory fake, including a failure at every derived write.
