# Canon: M6 implementation plan (The UI)

Status: **approved 2026-10-31** ("k1 yes, k2 yes": K1 and K2 as recommended). Decisions recorded as D63 and D64.

M6 replaces the M0 placeholder with the management app from the design doc ("Local management UI"): a React and TypeScript app embedded in the binary, served by `canon serve` on 127.0.0.1, and a thin client over the local API (`api/openapi.yaml`, 1.4.0). Every action it offers is already a CLI command. Today it only proves the token handshake.

Screens, in build order:

1. **Library:** a dense grid of every item (165 public, 16 drafts today), filtered by kind, surface, visibility and tag, with `/` to search. Thumbnails come from the local cache, so it works offline.
2. **Item editor** (`e`):
   - **Fields:** title, summary, why, date, tags and the other taxonomy fields, links, credits, alt text, visibility.
   - **Placements and copy:** placements per surface, with their settings, and per-surface copy.
   - **Facts:** shown read-only.
   - **Saving:** autosaves to the working manifest only.
3. **Plan review** (`p`): the plan as a readable diff with thumbnails, and **Apply**, the only button that touches the cloud.
4. **Ingest:** drop files; each one moves through detect, sanitize, verify and hash, with a red stop when verify finds leftover metadata.
5. **Jobs:** queue, progress, failures with the tool's output, and retry.
6. **Surface preview:** what each site will see after the next apply.

## 0. Decisions

### 0.1 Need your call

| # | Question | Recommendation |
|---|---|---|
| K1 | **What "surface preview" renders.** The design doc says "exactly what each portfolio will see". | **A faithful sketch per surface, plus what changes.** Each surface gets a small renderer with the site's real structure (art room halls, the DJ crate, the showroom and portfolio cards with their previews, the desktop grid and dock). It's built from `canon view <surface>`, with a "changes since the live view" list. The other option shows the real sites, each loading a local view through a `?canon=` override in its code. That's truly exact, but it needs a change in every site and both of them running locally. |
| K2 | **Styling.** | **Hand-written CSS with design tokens, no UI framework or component library**, as the M0 placeholder started. There's a light and a dark theme, and it's dense and keyboard-first ("quiet and fast, built for scanning"). It adds no dependencies and keeps the embedded bundle small. Tailwind is the alternative, if you'd rather edit styles that way later. |

### 0.2 Defaults I'll take unless you object

- **API gaps closed in Go:**
  - `getEvents`, the server-sent events stream: ingest, job, apply and sync changes, read with `fetch` so the bearer token still applies. It replaces polling, and `canon jobs --watch` uses it too.
  - `getDoctor`.
  - `getLocalBlob` and `getLocalDerived`: read-only, and limited to the cache.
  - Nothing new in the spec. These four have been in it since M1.
- **Saving:**
  - Every edit is a JSON merge patch with `If-Match` on the working revision.
  - A 412 (the CLI edited the same manifest meanwhile) reloads the item and keeps your unsaved field, with a note.
  - A validation error (422) shows on its field, and nothing is saved.
- **Placement settings:** forms are generated from each surface's placement schema (they're small: booleans, enums, URL lists, numbers), with a raw JSON field for anything unusual.
- **Plan and apply in the UI:** "Make plan" shows the plan with thumbnails; Apply runs exactly that plan and streams progress. A stale plan (D37) or a moved remote gets a clear message and a "plan again" button.
- **Routing:** hash routes (`#/items/<slug>`, `#/plan`...), no router library. Keyboard: `/`, `e`, `p`, `j` and `k`, `Esc`.
- **Libraries:** React and openapi-fetch (already there), with types generated from the spec as now. No state library: one small store over the API plus the event stream.
- **Security:** unchanged (D-guard). Host check, per-launch token, no CORS. The token leaves the URL fragment on first load, as M0 does. Phone access over Tailscale is still "later" (design doc).
- **Tests:**
  - Vitest with Testing Library, for every screen against a mocked API, with request and response shapes checked against the spec.
  - Go tests for the four endpoints.
  - One browser smoke test: `canon serve` on fixtures in headless Chrome. It loads the library, edits a title, makes a plan, and checks the working manifest changed.

**M6 is done when** each screen works against your real working manifest through `canon serve`, and the tests above pass. The proof is editing an item, planning, and applying from the UI, then checking that `canon plan` prints "No changes."

## Built (2026-10-31)

The six screens are in, plus a Doctor page, all over the local API (now 1.5.0, D65):
- **Library:** grid, filters, `/` to search, `j` and `k` to move, `e` to edit.
- **Item editor:** fields save on their own as merge patches with If-Match. A 412 reloads the item and reapplies the change once; a 422 shows its problems. Placement forms are generated from the placement schemas.
- **Plan review:** grouped ops with thumbnails, and Apply with live progress.
- **Ingest:** a dropzone, with each file's stages followed live.
- **Jobs:** the tool's output for failures, and retry.
- **Surface preview:** sketches of all seven surfaces, plus the changes against the live view.

The bundle is 84 KB gzipped, with React and openapi-fetch and no other runtime dependencies.

- **Go:**
  - `getEvents`: a server-sent events hub. Ingest, job, apply and sync events go out, and every write route publishes the sync state.
  - `getDoctor`.
  - Read-only local cache endpoints: `getLocalBlob`, `getLocalDerived`, and `getLocalThumbnail` (new) for the library grid.
  - `getSurfaceChanges` (new): the preview against the live view, computed server-side, since the public bucket's CORS rightly doesn't allow `canon serve`'s origin.
- **Tests:**
  - 23 Vitest tests over every screen, against a fake API that enforces If-Match and streams events.
  - Go tests for every new endpoint against the spec.
  - `TestUISmoke`: headless Chrome against the built UI and a real engine on in-memory buckets. It loads the library, checks thumbnails display, edits a title, makes a plan, applies it, then plans again to "No changes", and checks the edit reached the private bucket.
- **Found while building:**
  - The Content-Security-Policy (`default-src 'self'`) blocked the `blob:` URLs local images are shown through, so every thumbnail was broken. It now allows `img-src 'self' blob: data:`. The smoke test checks that thumbnails display.
  - The local endpoints were specified as octet-stream only, and the doctor's 503 wasn't in the spec at all.
  - A doctor report with no tools encoded `tools` as `null`.
- **On the real data:** every screen renders (checked read-only, with screenshots, through `canon serve`). The done criterion's edit, plan and apply ran in the smoke test, not on the real buckets. The working manifest had local edits made outside this session: five new items and about 30 changed, Boards, Cosmic Connect Four and The Gauntlet among them on the desktop. Applying would have published them, so that's your call.
