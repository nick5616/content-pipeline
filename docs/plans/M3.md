# Canon: M3 implementation plan (Plan and apply: blobs + manifest)

Status: **approved 2026-10-28** ("yes to all": F1 to F4 as recommended). Decisions recorded as D36 to D39.

M3 is the first milestone that touches GCS. It turns the local state (working manifest, blob cache, staged originals) into a reviewed plan, and applies that plan to the private and archive buckets. Publishing to the public bucket, views and jobs stay out (M4, M5). Everything is tested against fake-gcs-server; nothing in the test suite touches a real bucket.

## 0. Decisions

### 0.1 Need your call

| # | Question | Recommendation |
|---|---|---|
| F1 | **Item commands.** The M0 CLI stubs say `ls`, `show`, `item` and `taxonomy` land in M3, but the design doc scopes M3 to plan and apply. Without them, the only way to change a draft before M6 (the UI) is to hand-edit `working.json`. | **Build them in M3**, CLI and API: `ls`, `show`, `item new/set/rm`, `taxonomy ls/set`. Each one is a thin layer over `store.Update` (validate, then atomic write), and M5's publish tests need a way to flip visibility. The other option is read-only `ls`/`show` now and writes with the editor in M6. That makes M3 about a third smaller. |
| F2 | **What a saved plan pins.** Apply must write exactly what you reviewed, even if you keep editing between `plan` and `apply`. | **The plan records the working manifest's revision, and apply refuses if it changed** ("working manifest edited since this plan; run plan again"). The plan file stays small, and the manifest apply writes is byte-identical to the one the plan was computed from. The other option is to embed the whole manifest in the plan file. That lets you keep editing, but the plan file then holds every draft and private note. |
| F3 | **A remote object at a content-addressed path whose `sha256` metadata is missing or wrong** (hand upload, or corruption). | **Private bucket: re-upload** (op detail "checksum mismatch"; versioning keeps the old object). **Archive bucket: a plan error you have to look at.** The archive service account can't overwrite anyway (D14: create and view only), and a wrong original is worth a human look. |
| F4 | **Additive API change, 1.1.0 → 1.2.0.** The frozen spec can't express M3 as built: apply status is only reachable over SSE (`getEvents`), there's no op or summary count for the archive or history, and plans don't carry F2's revision. | Add `GET /api/plans/{id}/apply` (poll ApplyStatus, like ingest), `Plan.revision`, `summary.archive`, and OpType `write-history`. Nothing is removed or renamed. SSE stays with the UI in M6. |

### 0.2 Defaults I'll take unless you object

- **"Nothing to do" means no write ops.** Orphans are reported in the plan (summary count and `orphan` lines), and they never block the idempotency test. Otherwise one deleted draft would make every later plan non-empty until M8's GC.
- **Which originals get archived:** every file in `<cache>/originals/` (D34), whether or not a manifest asset points at it. **Which blobs get uploaded:** only those the working manifest references, drafts included, since the private bucket holds everything. A blob that's in the cache but unreferenced stays local.
- **Bucket paths:** private `blobs/sha256/ab/cd/<hash>.<ext>`, `manifest/manifest.json`, `manifest/history/<utc>-<hash16>.json`. Archive: `originals/sha256/ab/cd/<hash>.<ext>`, the same layout as the cache. Every object carries `x-goog-meta-sha256`. Uploads send a locally computed CRC32C, so GCS rejects corrupted transfers.
- **The private bucket can only receive bytes from the blob store.** The uploader takes a `blobstore.Blob` (made only by the blob store, which only takes `sanitize.Verified`), and the archive writer takes a `blobstore.ArchivedOriginal`. They are separate functions bound to separate buckets, so sending an original to the private bucket doesn't compile. Before each upload, the file is re-hashed and must match its name, which catches cache corruption.
- **Uploads never overwrite** (precondition `DoesNotExist`), except F3's private re-upload, which matches the existing generation. A 412 on a blob upload counts as success once the existing object's `sha256` matches, since another apply got there first.
- **Manifest write:** `ifGenerationMatch=G`, with G from the plan (0 when the bucket has no manifest yet). Then a history snapshot is written (`DoesNotExist`). History is its own op (F4), so a crash between the two leaves a plan with one `write-history` op, and a rerun converges.
- **Sync (D6, local half from M2):** `base.json` holds the remote manifest's bytes and generation. Status compares the base revision, working revision and remote generation (one metadata request). `plan` pulls silently when the remote moved and there are no local edits, and refuses when both moved (`diverged`). `canon pull --discard-local` resolves that. v1 never merges. After a successful apply, `base.json` becomes the applied manifest at the new generation.
- **Plans are kept** in `<state>/plans/<id>.json` (0600, outside the repo). `canon plan` saves one and prints its id, and `-o file` also writes a copy. `canon apply <id|file>` runs it. A plan with validation errors is never created; warnings go in `problems`.
- **Missing inputs are plan errors:** a referenced blob that's in neither the local cache nor the private bucket (with its item's slug). A missing original is only a warning (say, an item ingested on the Mac).
- **Config:** plan and apply need `privateBucket` and `archiveBucket`. `publicBucket` isn't used until M5.
- **Apply holds a local lock** in the state dir, so two applies from one machine can't interleave. Across machines, the generation precondition decides.
- **Retries:** the GCS client's own retries cover transient errors, since every write is conditional and therefore idempotent. Apply stops at the first op that still fails. Everything up to that point is safe to keep, and the next plan only lists what's left.

## 1. Ordering and crash safety

```
archive-original   (archive)  originals/sha256/...   DoesNotExist
upload-blob        (private)  blobs/sha256/...       DoesNotExist (or F3 re-upload)
write-manifest     (private)  manifest/manifest.json ifGenerationMatch=G
write-history      (private)  manifest/history/...   DoesNotExist
orphan             reported only
```

Within a phase, ops are sorted by path, so a plan is deterministic. If apply dies anywhere before `write-manifest`, the remote manifest still points only at blobs that exist. If it dies after, the manifest is complete and only history is missing. In every case the next `plan` lists exactly the remaining ops.

## 3. Tests

| Property | Test |
|---|---|
| Correct diff | Table tests on `Diff`: empty bucket; all present; checksum mismatch (private re-upload, archive error); missing local blob present remotely (no op); missing everywhere (error); two items sharing a blob (one upload); history missing for the current manifest (one `write-history`); unreferenced remote blob (orphan, not a write). |
| Plan output | Golden files for `Render` and the plan JSON. Plan JSON validates against `openapi.yaml`. |
| Deterministic | The same inputs give byte-identical plan JSON (apart from the id) and identical op order. |
| **Idempotent** (definition of done) | Against fake-gcs-server: ingest the media fixtures, plan, apply, plan again → no write ops. Run at the end of every integration scenario below. |
| Concurrency safe | Change the remote manifest between plan and apply → apply refuses (409 / exit 1) and writes nothing. Edit `working.json` between plan and apply → refuses (F2). |
| Fault tolerant | Using the fault fake: fail at op N for every N; return 503s; cut an upload mid-stream; cancel the context. Each time, a rerun of plan + apply converges to the same end state as a clean run, and the second plan is empty. A cut upload leaves no object behind. |
| Archive boundary (D14) | After a full apply, no object in the private bucket has an original's sha256, and every archive object's bytes hash to its name. The uploader and archive writer are compile-time separated (§0.2). |
| Integrity | Every uploaded object has `sha256` metadata matching its bytes. A corrupted cache file (bytes don't match its name) stops apply before upload. |
| Sync | Status for each of the five states. Pull fast-forwards, refuses with local edits, and `--discard-local` takes the remote. First apply to an empty bucket uses generation 0. |
| Offline | With GCS unreachable, status says `offline`, plan and apply fail with a clear message (503 in the API), and ingest and item edits still work. |
| API | Every new handler is contract-tested against `openapi.yaml` 1.2.0; the CLI-twin test covers the new operations. |
| Item commands (if F1) | `item set` with an invalid value changes nothing and reports why; `If-Match` with a stale revision gets 412; `item rm` refuses an item that's live in the remote manifest. |

**M3 is done when** all of the above pass in WSL, and `canon ingest testdata/_out/media && canon plan && canon apply <id> && canon plan` against fake-gcs ends with "No changes."

## 4. Trying it for real (your side, after M3 is built)

Needs the earlier open items: ADC login, a config file with bucket names and region, and the provisioning script run with `--apply`. Then `canon plan` shows what would go up, and `canon apply` sends it. The first real apply uploads your drafts' sanitized blobs to the private bucket and the untouched originals to the archive. Nothing reaches the public bucket until M5.

## Built (2026-10-28)

Everything above is in, and the done criterion holds with the real binary: `canon ingest testdata/_out/media` (14 drafts; the 6 hostile files refused), then `canon plan` (14 to archive, 14 to upload), `canon apply` (30 ops), and `canon plan` again prints "No changes." Additions found while building:
- **Base on disk:** `base.json` holds the remote manifest's exact bytes, and `base.meta.json` its generation and SHA-256. A torn pair reads as "no base", which makes the next status `behind` or `diverged` rather than wrong.
- **Crash between the manifest write and recording base:** status sees that working already equals the remote and reports `behind`, not `diverged`, so the next plan pulls and is empty. Tested.
- **Every GCS write is conditional:** the `gcs.API` has no unconditional write at all. fake-gcs-server enforces generation preconditions and rejects a wrong CRC32C, so both are covered by the integration tests, not only by the in-memory fake.
- **`createPlan` can return 409** (local and remote both moved); added to 1.2.0 with D39.
- **`item rm` and published items (D40), apply without a prompt (D41).**
- **Tests:** fault injection fails every write in turn, cuts an upload mid-stream, returns 503s on listing, and cancels the context; each run converges to a clean run's end state with an empty second plan. Test environments ingest each fixture set once per test binary and copy it, which took the apply tests from 66s to 8s.
- **CLI-twin test** now resolves the whole command path (`canon taxonomy set`, not just `canon taxonomy`); placeholder commands for later milestones are marked as stubs.
